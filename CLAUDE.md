# GlobalPride-Admin

Admin dashboard SPA. React 19 + TypeScript + Vite 8, Tailwind CSS v4, React Router 7, Zustand, Axios, Recharts. Package manager: **yarn (v1)**.

## Commands

- `yarn dev` — start dev server
- `yarn build` — typecheck (`tsc -b`) then production build. Run this to verify changes.
- `yarn lint` — ESLint
- `yarn preview` — serve the production build

There is no test runner set up.

## Structure

```
src/
  api/
    axios/client.ts        # shared axios instance + interceptors (auth header, 401 → refresh → retry, error normalization)
    services/              # one file per API domain, e.g. authService
    utils/                 # token/refresh helpers, unwrap, isApiSuccess, handleApiError, raw (defensive readers), mutate
  components/              # reusable UI primitives, all prefixed `WebApp*`
  config/env.ts            # typed access to VITE_* env vars
  hooks/                   # zustand stores / hooks (useAuth = persisted auth store, useSettings = persisted settings cache)
  layouts/AdminLayout.tsx  # authenticated shell: Sidebar + Topbar + <Outlet />
  pages/                   # route screens, re-exported from pages/index.ts (dashboard/ has its own folder)
  routes/RequireAuth.tsx   # guard for protected routes
  types/                   # shared types + module augmentation (axios.d.ts, env.d.ts)
  store/                   # in-memory caches of API data (createQueryStore), one file per domain
  utils/                   # cn() class helper, appToast, formatting helpers
```

## Conventions

- Import from `src` via the `@/` alias (e.g. `@/components/Button`), not long relative paths.
- Named exports for components and pages (`export const Dashboard = ...`). `App`, `RequireAuth` and `AdminLayout` are default exports.
- Styling is Tailwind only. Merge class names with `cn()` from `@/utils/cn` so a caller's `className` overrides defaults.
- Brand colors live in the `@theme` block of `src/index.css` (`--color-primary` → `bg-primary`, `text-primary`, …). Add new tokens there rather than hard-coding hex values.
- UI components accept `className` for the main element and `containerClassName` for the outer wrapper.
- Build pages from the existing `WebApp*` components (`Card`, `PageHeader`, `Button`, `Input`, `Modal`, `Badge`, `Avatar`, `DetailList`, …) before writing new markup.
- New protected routes go inside the `<AdminLayout />` route in `App.tsx`, and get a sidebar entry in `src/layouts/Sidebar.tsx`. Route paths are lowercase.
- Forms use react-hook-form + yup (`yupResolver` from `@hookform/resolvers/yup`). Put schemas in `src/schemas/` and derive types with `yup.InferType`. Spread `{...register("field")}` onto `WebAppInput` / `WebAppTextarea` / `WebAppCheckbox` and pass `errors.field?.message` as `error`; wrap `WebAppSelectInput` in a `Controller`. Add `noValidate` to the `<form>` so yup's messages are shown, not the browser's.
- Charts use Recharts; pass colors as CSS vars (e.g. `var(--color-primary)`) so they follow the theme.

## API & auth

- Use `apiClient` from `@/api/axios/client`; add calls to a service in `src/api/services/`.
- Pass `{ useAuth: true }` in the request config to send the Bearer token. Only those requests attempt a token refresh on 401.
- Rejected requests reject with a normalized `ApiError` (`message`, `status`, `code`, `errors`) — see `src/api/types/response.ts`. Request bodies go in `src/api/types/request.ts`, response types in `src/api/types/response.ts`.
- Backend responses are shaped as `ApiResponse<T>` (`success`, `data`, `message`, `errorCode`, `errors`), the same backend as the mobile app, except `/identity/*`, which uses `AdminResponse<T>` (see Notes). A 200 can still carry `success: false`: in services, return `unwrap(data)` from `@/api/utils` (throws an `ApiError`); in components, `isApiSuccess(data, fallback)` toasts failures. Show a caught error with `handleApiError(error)`. `errors` holds the real cause; `message` is often generic.
- Toasts: `appToast.show(title, message, "success" | "error" | "info")` from `@/utils/appToast`, rendered by `WebAppToaster` in `App.tsx`.
- The refresh call (`refreshToken` in `src/api/utils/index.ts`) uses its own bare axios instance, not `apiClient`, so it can't loop through the 401 interceptor. Don't import `apiClient` into `src/api/utils`.
- Auth state (`token`, `refreshToken`, `user`, `isAuthenticated`) lives in `useAuth` and is persisted to localStorage. Call `useAuth.getState().login({ token, refreshToken, user })` after a successful login; `logout()` clears it.

## Environment

Copy `.env.example` to `.env`. Variables: `VITE_API_URL`, `VITE_APP_NAME`, `VITE_API_VERSION` (typed in `src/types/env.d.ts`). `.env` is git-ignored.

## Notes

- API data is cached in memory in `src/store/` (not persisted; cleared on sign-out by `useAuth().logout`). Each cached call is a `createQueryStore(fetcher, { keyOf, staleTime })`: pages read it with `useQuery(...args)`, which returns cached data immediately and only refetches when it's missing or older than `staleTime` (default 5 min), sharing in-flight requests; `refresh()` forces a refetch (pages show a Refresh button). After a mutation, update the cache with `setData` / `setAllData` / `remove`, or mark it stale with `invalidate` — put those mutations in the store file (e.g. `suspendUser` in `usersStore.ts`), not in pages. Search, filtering, sorting and paging of cached lists happen in the browser, not via API params. Paged admin endpoints return `PagedResult<T>` (`items`, `pageNumber`, `pageSize`, `totalCount`, `totalPages`). Activity feeds share `ActivityItem` and `activityStyle` (`src/pages/shared/activityStyle.ts`).
- The Dashboard (`/dashboard`) reads `GET /admin/dashboard` through `dashboardStore` (cached per range for 2 minutes); the `?range=` search param (`today`, `7d`, `30d` default, `90d`, `all`) is passed straight to the API, and its charts cover at most the last 90 days. Some API timestamps are UTC without an offset — read them with `parseApiDate` (`src/utils/format.ts`). Every page reads the API; there is no mock data. User Management (`/users`, `/users/:userId`, `/users/:userId/activity`) uses `usersStore` (`src/store/usersStore.ts`) over `usersService` (`/admin/users`). The list store fetches every user once (`listAll`: all pages at the API maximum of 100), then search (name, email, phone — `0803…` matches `+234803…`), status / restricted filter, sorting and paging run in the browser; those filters live in the URL (`?q=`, `?status=`, `?sort=`, `?dir=`, `?page=`). Details and the activity feed (server-paged, `?type=` / `?page=`) are cached per user. `suspendUser` / `activateUser` / `liftUserRestriction` / `deleteUser` update the cached list and details and mark the dashboard stale. Delete is refused with 409 for users with wallet transactions or sent campaigns, and the dialog then offers Suspend instead. The activity `type` filter only offers names the API accepts (it 400s on unknown ones). Campaign Management (`/campaigns`, `/campaigns/:campaignId`, `/campaigns/:campaignId/recipients`) uses `campaignsStore` over `campaignsService` (`/admin/campaigns`). URLs use the public reference (e.g. `GP-2026-605233`); the API accepts it or the GUID. The list store fetches every campaign, then search (name, reference, user, sender), status / type filters, sorting and paging run in the browser (`?q=`, `?status=`, `?type=`, `?sort=`, `?dir=`, `?page=`). Details show the campaign, a log built from its timestamps, a recipient preview and the delivery report (`DeliveryReportCard`): its `reportState` decides what is shown (`not_applicable` = Audience Marketplace or not sent, `summary_only` = totals only, `awaiting_receipts` / `final` = per-recipient tracking, with "Check for new receipts" calling the rate-limited refresh). The recipients page has an Addressed view (`/recipients`) and a Delivery Status view (`?view=delivery`, `/delivery-report/recipients`), both fetched in full and searched / filtered in the browser; CSV export downloads `/delivery-report/export` with the auth header. List filters on every page use `useListParams` (`src/hooks/useListParams.ts`). Pricing Management (`/pricing`) reads `GET /admin/pricing` through `pricingStore` (campaign prices, VAT rate, referral bonus); each edit is a `PUT /admin/pricing/campaign/{key}` / `/vat` / `/referral-bonus`, which returns the full updated settings that replace the cache. Only `active` campaign prices are editable (voice / video are `coming_soon` with a null price), and only the referral bonus amount can be changed (reward type and trigger are fixed by the API). Promotions (`/pricing/promotions`) use `promotionsStore` over `promotionsService` (`/admin/promotions`): every promotion is fetched and filtered in the browser (`?status=`, `?appliesTo=`); create / edit (`name`, `discountType`, `discountValue`, `appliesTo`, `startDate` / `endDate` as yyyy-MM-dd) and delete (prices go back to normal straight away). The status (active / scheduled / expired) comes from the dates, so the form has no status field. Audience Marketplace (`/audience-marketplace`, `/audience-marketplace/records/:recordId`, `/audience-marketplace/states`, `/audience-marketplace/states/:stateId/lgas`, `/audience-marketplace/lgas`) uses `audienceStore` over `audienceService` (`/admin/audience`). `:stateId` is the URL-encoded state *name* (the API identifies states and LGAs by name). The summary, states (all 37, zero when empty) and per-state LGAs are cached and searched in the browser; `/lgas` has no all-LGAs endpoint, so `allAudienceLgasQuery` loads every state with `lgaCount > 0`. Contacts (`/records`) are the exception to browser-side filtering: there can be far too many, so search (phone prefix or name, debounced), state, LGA, gender and page go to the API and live in the URL (`?q=`, `?state=`, `?lga=`, `?gender=`, `?page=`). Uploads send .csv / .xlsx files as multipart (`POST /upload`, re-uploading is safe) and show per-file added / already stored / repeated / rejected counts; Delete removes a state's or LGA's contacts (`DELETE /records?state=&lga=`). Both mark all audience data stale. While `summary.isSampleData` is true the counts are built-in demo data, there are no contacts, and Delete is hidden. There is no state / LGA activation in the API. Swagger documents no body for records, upload or delete results, so `audienceService` reads those defensively (first of several likely field names); tighten the types once they are documented. Wallet Management (`/wallets`, `/wallets/transactions/:transactionId`) is read-only and uses `walletsStore` over `walletsService` (`/admin/wallets`): the summary cards, every transaction (fetched in full, then search by reference / GUID / user name, `?category=`, `?status=`, `?range=` and `?page=` run in the browser) and one transaction by reference (`GP-TRX-…`) or GUID. API amounts are positive with a `direction` (credit / debit); `signedAmount` adds the sign. Transaction details' `currentWalletBalance` is the user's balance now, not after that transaction. Helpers live in `walletOptions.ts` (`categoryIcon`, `walletStatusStyle`, `paymentMethodLabel`). `fetchAllPages` / `MAX_PAGE_SIZE` are shared from `src/api/utils/fetchAllPages.ts`. Finance & Reports (`/finance`, `/finance/reports/:reportId` — `revenue`, `vat`, `wallet-funding` (API name `funding`), `referral-bonuses`, `refunds`) is read-only and uses `financeStore` over `financeService` (`/admin/finance`): the summary (`/summary?from=&to=`: headline figures, revenue per service, VAT rate and a per-day series charted with the dashboard's `RevenueChart`) and each report's rows, paged by the API (`/reports/{report}?from=&to=&page=`). Report definitions (summary cards, breakdown, columns) are in `src/pages/finance/reports.tsx`. CSV export downloads `/reports/{report}/export` with the auth header (at most 50,000 rows). The period lives in `?period=` (`useReportPeriod`, default Last 30 Days) and is sent as `from` / `to` days; report pages also keep `?page=`. Swagger documents no finance bodies, so `financeService` reads them defensively; tighten the types once documented. Referral Management (`/referrals`, `/referrals/:referralId`) is read-only and uses `referralsStore` over `referralsService` (`/admin/referrals`): the summary cards (`/summary`, including `currentBonusAmount`, which pending referrals without a bonus amount show), every referral (fetched in full, then search by code / referrer / referred user / invited contact, `?status=`, `?bonus=`, `?range=` and `?page=` run in the browser) and one referral by GUID. Swagger documents no list or details body, so `referralsService` reads rows defensively (first of several likely field names; status also accepts the mobile enum, 2 = bonus credited); tighten the types once documented. Without a bonus status from the API, a successful referral counts as paid. Changing the referral bonus in Pricing marks the referral summary stale. Advertisement Management (`/advertisements`, `/advertisements/new`, `/advertisements/:advertisementId`, `/advertisements/:advertisementId/edit`) uses `advertisementsStore` over `advertisementsService` (`/admin/advertisements`): the summary cards (`/summary`), every advertisement (fetched in full, then search by name / code / advertiser, `?status=`, `?placement=`, `?from=` / `?to=` start date and `?page=` run in the browser) and one ad by code (`AD-1001`, used in URLs) or number. Create and edit send multipart form data (`Name`, `Advertiser`, `Description`, `CtaLabel`, `DestinationUrl`, `Placement`, `StartAt`, `EndAt` as UTC ISO date-times, `Creative` image: jpeg / png / gif / webp, at most 5 MB, required on create, omitted on edit to keep the current one). Pause / resume / end / delete are in the store and update the cached list and details. An ended ad can't be resumed or edited. Swagger documents no ad body, so `advertisementsService` reads rows defensively (first of several likely field names; status falls back to the schedule; relative creative URLs are resolved against the API's site root); tighten the types once documented. Ads with no `impressions` show "Tracking data unavailable". Support (`/support` tickets, `/support/tickets/:ticketId`, `/support/articles`, `/support/faqs`, plus `/new` and `/:contentId/edit` under each) uses `supportStore` over `supportService` (`/admin/support`). Tickets: the summary cards (`/tickets/summary`, falling back to counting the list), every ticket (fetched in full, then search by reference / subject / user, `?status=`, `?category=`, `?priority=` and `?page=` run in the browser, newest activity first) and one ticket by reference (`TKT-…`, used in URLs) or GUID. Status / priority changes, replies (seen by the user; the API moves the ticket to Pending User) and internal notes are store actions. Categories are free text from the app (`issueCategory`), so filters add any unknown ones and labels fall back to the raw value. Articles and FAQs are fetched in full (`status=all`) and filtered in the browser (`?q=`, `?category=`, `?status=` — `published` / `draft`, shown as Unpublished); edit and preview load the item by GUID for its body. Create / edit send `publish` with the body; after an edit the store calls `/publish` or `/unpublish` if the saved status differs from the one chosen. Articles also have an optional `summary`. Swagger documents request bodies but no response bodies, so `supportService` reads rows defensively (mobile DTO names first: `reference`, `issueCategory`, `from`, `content`, `question`, `answerHtml`); tighten the types once documented. Articles and FAQs share one shape (`AdminHelpContent`) and one list / form (`HelpContentList`, `HelpContentForm`), with wording per kind in `helpContentKinds`. Their bodies are HTML from `WebAppRichTextEditor`; run them through `sanitizeRichText` (`src/utils/richText.ts`) before saving or rendering. Row "⋮" menus use `WebAppActionMenu`. List / item load and error states are `ListLoadState` / `ItemLoadState` (`src/pages/support/SupportParts.tsx`, also used by Notifications and Compliance), and page refresh buttons are `RefreshButton` (`src/pages/shared/`). Notifications (`/notifications`, `/notifications/new`, `/notifications/:notificationId`, `/notifications/:notificationId/edit`) are admin announcements to all users, via `announcementsStore` over `announcementsService` (`/admin/announcements`). There is no admin feed of system notifications, so only announcements are listed. URLs use the code (`NOT-000012`); the API also accepts the number. Summary cards (`/summary`, falling back to counting the list), every announcement fetched and filtered in the browser (`?q=`, `?status=` — scheduled / sending / sent / cancelled, `?page=`). Create / edit send `title` (≤100), `message` (≤500), `delivery` (`now` / `later`) and `scheduledAt` (the local date and time converted to UTC ISO). Only scheduled announcements can be edited or cancelled (`/cancel`); cancelled ones stay in the history. Turning off "Allow Admin Announcements" in Settings blocks Create Notification. Compliance (`/compliance` = Flagged Activities, `/compliance/flags/:flagId`, `/compliance/content-reports`, `/compliance/campaigns`, `/compliance/user-activity`, `/compliance/audit-logs`, `/compliance/disclaimers`) uses `complianceStore` over `complianceService` (`/admin/compliance`). Flags, content reports and flagged campaigns are fetched in full and filtered in the browser (URL params; `?status=open` means pending + under review); flag URLs use the code (`FLG-0012`). Flags move Pending Review → Under Review (`/start-review`) → Resolved (`/decision` with `campaign_cancelled` / `user_suspended` / `user_restricted` / `no_further_action`; the API applies the action, so users / campaigns / dashboard caches are marked stale) or Dismissed (`/dismiss` with a reason); notes go to `/notes`. A review action marks the summary, reports, flagged campaigns and audit log stale. Campaign Compliance lists only campaigns flagged at least once. The audit, disclaimer and user activity logs are paged and filtered by the API (debounced `?q=`, `?from=` / `?to=`, activity `?type=` from `activityTypeOptions`, `?page=`); audit records link to flags, campaigns, announcements, ads, tickets and transactions by their code prefix (`recordLink`). Swagger documents no compliance bodies, so `complianceService` reads them defensively. `/compliance/flagged-activities` redirects to `/compliance`. Section tab bars use `WebAppTabs`, and the reply / note boxes use `NoteComposer` (`src/pages/shared/`, `onSubmit` may return a promise; the text is kept if it resolves to false). Settings (`/settings` = General, `/settings/notifications`, `/settings/security`, `/settings/platform`) uses `settingsStore` over `settingsService` (`/admin/settings`): `GET` loads all three sections, each form saves with `PUT /general` / `/notifications` / `/security`. `AdminLayout` loads the settings on sign-in, and every load or save also updates `useSettings`, a cache persisted to localStorage, so the login page (before the API can be called) shows the last platform name and logo, and the sidebar logo, idle timeout (`useIdleTimeout`, 5–1440 minutes), strong-password rule (upper, lower, number, special character, via the Change Password resolver `context`) and "Allow Admin Announcements" read it synchronously. Only `settingsStore` writes to `useSettings`. The logo is sent as a data: URI (png / jpeg / webp, ≤ 290 KB file). The default time zone is saved but not yet applied to date formatting. Platform Information shows the EBulkSMS balance (`/sms-balance`; gateway problems come back as `available: false` with a message) and every field `/system-info` returns.
- Auth uses the admin Identity API (`/identity/login`, `/identity/refreshToken`, `/identity/logout`, `/identity/me`), not the mobile app's `/auth/*`. Its responses use the `AdminResponse` envelope (`isSuccess`, `result`, `code`, `details`); `unwrap`, `isApiSuccess` and the client's error normalizer accept both envelopes via `normalizeResponse`. `authService.login` rejects accounts whose `role` isn't an admin role. The signed-in admin (`AdminProfile`) is kept in `useAuth().user`; read display details with `useCurrentAdmin()`. Sign out with `authService.signOut()` (clears local state, then revokes the session server-side, best-effort). The login page shows the platform name, logo and support email from `useSettings`. Backend Swagger: `https://zairapay.com/globalpride/swagger/v1/swagger.json`.
- Every sidebar link now has a page. Profile (`/profile`) loads and saves through `GET` / `PUT /identity/me` (`authService.me` / `updateProfile`, which update `useAuth().user`), and Change Password (Account Settings) calls `POST /identity/change-password`. Swagger documents request bodies but few admin response bodies, so services for undocumented endpoints read rows with the helpers in `src/api/utils/raw.ts` (each field from the first of a few likely names) and send mutations with `mutate` (`src/api/utils/mutate.ts`), which accepts an empty `result`. Stores then update caches from the returned item, or apply the known change locally and refetch. Tighten the types once sample responses are available.
- Staying on TypeScript 6 until typescript-eslint supports TypeScript 7. Don't use the deprecated `baseUrl` tsconfig option.
